FluidMotion goes universal: one honest per-source motion status for every server, the experimental screen-capture pipeline (default OFF, consent only), and the documented-API hardware MEMC survey - with the same hard rule as always: genuine MEMC is never claimed where frames are not accessible.

Fixes
- Per-source motion status: the Motion panel now carries an accurate status line from the fixed vocabulary - "Adaptive frame pacing active" on our owned playback surface (real Surface.setFrameRate matching plus the dropped-frame watchdog - frame pacing, never called interpolation), "Native high-frame-rate playback" when the measured content rate is genuinely high, "Interpolation unavailable - provider embed (frames not accessible)" for every provider embed (their frames live inside cross-origin iframes and cannot be read by platform design), and "Stability optimization active" whenever StabilityGuard has the motion work yielded during recovery
- Experimental capture MEMC (default OFF): the one authorized route to provider frames - the platform's own MediaProjection consent dialog - now has a real capture pipeline on the native side: MediaProjection + VirtualDisplay + ImageReader at half-display resolution (720p cap), real frame intake with measured capture-to-intake latency, and a real block-matching motion field over the captured frames. It reports "experimental pipeline not yet generating frames" because it does NOT synthesize frames yet - nothing in this build ever claims generated output that was not generated
- Capture guardrails are enforced in code: capture never starts without the platform consent dialog (a declined dialog leaves the feature off), measured latency above 250ms auto-disables the mode to protect A/V sync, the pipeline yields at StabilityGuard level 2 and auto-disables itself at level 3 (instability rejects the feature automatically), the capture is session-scoped (leaving the player tears it down), and the feature is off by default in settings
- Hardware motion enhancement survey (documented APIs only): Android exposes no documented MEMC / motion-enhancement API. The two surfaces that look related were probed and correctly labeled - Display.hdrCapabilities reports HDR dynamic-range types (not motion processing) and the decoder's VideoCapabilities frame-rate range is codec capability (not motion enhancement). The honest status is "Unsupported by current hardware"; "Hardware motion enhancement active" is reserved for a documented-API detection that does not exist
- The status vocabulary is QA-locked: genuine MEMC is only ever claimable behind real generated frames (none exist), provider embeds always carry the frames-not-accessible line, and the capture pipeline's generating flag cannot be set true anywhere in the code
- Subtitle sync fix (matches the web estimator, now v4): users reported subtitles both delayed and, at speed, "so fast / ahead of the voices". Root cause: provider timeupdates are thinned and transport-late (they describe where the video WAS), and a caption clock must neither hard-reset to every message (delay) nor trust a claimed playback rate (runaway ahead during stalls). The caption timeline is now the web build's v4 staleness-aware estimator: it MEASURES the real playback speed from provider position deltas and the measured rate wins over any claimed rate (claimed is fallback only - it follows real 1.5x/2x speed changes and ignores implausible samples), it FREEZES with buffering stalls on evidence (provider still messaging but the position frozen for 1.2s, or total silence 8s - sparse-but-healthy providers never false-freeze), its transport-lag correction runs only when a new position message arrives (never per tick), snaps to truth only on real jumps with a full speed re-measure afterwards, uses provider truth while paused/scrubbing, and can never move captions backward while playing (only a real seek can). The subtitle offset and position controls keep working exactly as before. Physical-device confirmation on TVs is pending - verified at the code level (QA lock + build)
- The experimental capture runs as a documented mediaProjection foreground service (the Android 14 requirement), API-guarded down to Android 7, with the projection handed off in order: consent, foreground service, projection, virtual display

Honest limits
- No interpolation frames are generated anywhere in this build. The capture pipeline performs real frame intake and real motion estimation; the synthesis stage is the documented next step. The status line says exactly that, on every screen
- Provider-iframe interpolation remains impossible without provider cooperation - cross-origin pixels are not readable by platform design, and this project will not bypass that. The adapter and the capture pipeline are the authorized alternatives
- Capture-mode A/V latency cannot be eliminated (the capture path itself delays frames); the measured value is shown live in the panel and the auto-disable guard keeps it from ever being harmful
- The capture-to-intake latency is measured against the Image timestamp in the same monotonic clock domain; samples outside 0-2000ms are discarded, never faked, and "Unavailable" is shown until a real sample lands
- Manufacturer TV-side motion enhancement (the panel's own MEMC) applies to any HDMI input and needs no app support - it is documented here, never claimed by us
- Physical TV verification of the capture pipeline, the frame-rate matching and the subtitle clock fix remains pending; this build is verified at the code level (QA locks + clean Gradle build)

Locked by native QA (status honesty, capture guardrails, subtitle-clock estimator v4 and player-shape rules must stay). Builds at 0.220.
